# 검색 개선 실험 기록

규칙(Mini-project 자료 52쪽): 한 번에 하나만 바꾸고, 같은 평가셋으로 다시 잰다.
평가셋: `evaluation/cases.json` 44문항 중 rag 23문항 (모두 draft → **잠정 수치**).
지표: Hit@5(정답 청크가 상위 5개 안), Mean recall(정답 청크 중 찾은 비율), MRR(1/첫 정답 순위의 평균).

## 0. Baseline — v13b-the-new-avante (2026-10-24)
- 결과: Hit@5 21/23 (0.913) · recall 0.805 · MRR 0.472 → `results/retrieval_v13b.json`
- 첫 정답 순위 분포: 1위 6 · 2위 4 · 3위 3 · 4위 5 · 5위 3 · 없음 2 → "찾지만 순위가 낮다"
- 실패: CG-05(정차와 주차 차이, 제2조), CG-15(아반떼 엔진오일 교환 주기, 정기 점검표)

## 1. 실험 01 — BM25 검색어 동의어 확장 (`exp01_query_synonyms.py`)
- 원인 분석: BM25 단독 순위에서 CG-05 정답 26위. 질문 "달라" ↔ 조문 "~란 … 말한다", "교환" ↔ "교체".
- 변경: BM25 검색어 뒤에 동의어 추가 `교환/갈아→교체, 주기→정기 점검, 달라/차이→뜻 란 정의`. 임베딩·필터·top-k·인덱스 동일.
- 결과: Hit@5 0.913→0.957 · recall 0.805→0.848 · MRR 0.472→0.519. CG-05 없음→1위, CG-13 4위→3위. 하락 문항 없음.
- 한계: 실패 문항을 보고 만든 사전(과적합 위험), 실질 개선 1문항. CG-15는 그대로 실패 → 원인은 표현이 아니라 청크 구조.

## 2. 실험 02 — 정기 점검표 항목 단위 보조 청크 (`exp02_table_rows.py`)
- 원인 분석: 정답 청크가 1,000자 안팎의 점검표 하나에 항목 수십 개가 섞여 점수가 희석됨.
- 변경(실험 01 위에 1개 추가): 점검표 청크 12개에서 항목 한 줄씩 135개 보조 청크(`content_role=table_row`,
  `parent_chunk_id`)를 만들어 추가 색인 → 인덱스 `v14-table-rows` (기존 2,406 + 135 = 2,541).
  기존 청크·임베딩·ID는 그대로(보조 청크만 임베딩), 검색 결과는 원래 표 청크로 묶어 반환(small-to-big).
- 검증(OpenAI 없이): 보조 청크가 없는 v13b에서 `grouped_search` 결과가 `core.search`와 23문항 모두 동일.
- 결과(2026-10-24): Hit@5 0.957→0.957 · recall 0.848→0.848 · MRR 0.519→0.515 (실험 01 대비)
  - 순위 변화: CG-10(K5 엔진오일 교환 주기) 4위→2위 / CG-09 2→3, CG-18 2→3 (하락) / CG-15 여전히 실패
  - CG-15 원인 재분석: 상위 결과가 "엔진 오일 및 필터 교체"(교체 주기를 '준수하라'는 문장만, 숫자 없음),
    "통상 조건" 머리말(주기표 설명) 등 '교체 주기'라는 말을 직접 쓰는 청크들. 정답(숫자가 있는 표 행)은
    보조 청크로도 BM25 묶음 순위 6위. 질문 어휘와 가장 겹치는 건 '주기를 설명하는 글'이지 '주기 값이 있는 표'가 아님.
  - 판정: **채택하지 않음.** 지표 개선이 없고 1문항 상승/2문항 하락, 서비스 반영 시 검색 코드 변경 부담도 있음.
- 배운 점: 청크를 잘게 쪼갠다고 순위가 오르지 않는다. 질문("주기는?")과 정답(숫자 표)의 표현 방식이 다르면
  쪼갠 행도 '설명하는 글'에 진다. 다음 후보: 표 행에 "교체 주기는 …" 같은 자연어 요약 문장을 붙이거나(HyDE 반대 방향),
  질문 의도(주기/값 질문)에 따라 표 청크에 가산점을 주는 방식.
- 알려진 한계: PDF 줄바꿈 때문에 일부 항목명이 잘림(예: K5 가혹 조건 "…스마트스트/림 G2.0"). 서비스 반영 시
  rag 서버 검색에도 같은 묶기(parent 반환)가 필요 — 지금 `core.search`는 보조 청크를 그대로 돌려준다.

## 3. 실험 03 — LLM 재정렬 (`exp03_llm_rerank.py`)
- 원인 분석: 실험 01 기준 Hit@5는 0.957이지만 첫 정답이 4~5위인 문항이 많아 MRR 0.52. "찾지만 순위가 낮다".
- 변경(실험 01 위에 1개 추가): 후보 15개(core.search top_k=15) → gpt-4o-mini(temperature 0)가 관련도 순으로 재정렬
  → 상위 5개 평가. 인덱스 v13b·임베딩·필터 동일. LLM 오류 시 원래 순서로 대체(평가 중단 없음).
- 함께 기록: `pool15`(후보 15개 안에 정답이 있는 비율 = 재정렬로 도달 가능한 상한), 문항당 지연·토큰(운영 점검 54쪽).
- 검증(OpenAI 없이): 가짜 LLM 응답 4종(정상·일부 누락·깨진 JSON·범위 밖 번호)으로 순서 처리 확인.
- 결과(2026-10-24, 1회 실행): Hit@5 0.957→**1.000** · recall 0.848→0.930 · MRR 0.519→**0.800** (실험 01 대비)
  - 상한(pool15): Hit 1.000 · recall 0.979 → 후보 15개 안에 정답이 모두 있었고, 재정렬이 그걸 위로 끌어올림
  - 첫 정답 1위 문항 7→16개 (MRR 18.4/23 = 0.800으로 재계산 일치). CG-15 실패→1위(정기 점검표 통상·가혹 두 청크가 1·2위)
  - 하락 2건: CG-06 1→5위 — 시행령 제10조의3(소화전 주변 주차 금지의 구체 규정)을 제32조보다 앞에 둠.
    평가셋 정답 지정이 좁은 탓일 수 있음(시행령도 타당한 근거) → 정답 청크 검토 필요.
    CG-30 1→5위 — '황색 점멸' 질문에 '황색 등화(점등)' 조문을 1위로 둔 진짜 오류. 정답 청크 본문이 띄어쓰기 없이
    붙어 있음("차마는다른 교통…")도 영향 가능(추론).
  - 운영: 재정렬 23회 실패 0 · 지연 평균 1,058ms / 최대 1,804ms · 토큰 평균 입력 3,633 / 출력 34 (gpt-4o-mini)
  - 2회차(같은 설정 재실행, results/exp03_*.json은 2회차로 덮어씀): MRR **0.857** · recall 0.930 · Hit 1.000,
    첫 정답 1위 18개(MRR 19.7/23 재계산 일치). 1회차와 다른 문항: CG-06 5위→1위(유지), CG-01 2위→1위.
    CG-30은 두 번 모두 5위 → 우연이 아닌 재현되는 오류. 지연 평균 986ms / 최대 1,450ms.
    → 2회 MRR 0.800 / 0.857 (평균 0.83). temperature 0이어도 LLM 순위가 문항 1~2개씩 흔들린다.
  - 판정: **효과 큼, 서비스 반영 후보.** 단 질문당 LLM 호출 +1회(약 1초)·비용 증가, 실행마다 소폭 달라질 수 있어 반복 측정 필요.

## 4. 서비스 반영 — 실험 03(LLM 재정렬)을 rag 서버에 적용 (2026-10-25)
- `core.rerank_hits()`: 실험 03의 재정렬 로직을 서비스용으로 옮김. 실패(타임아웃·깨진 JSON·잘못된 번호) 시 검색 순서 유지.
- `server.Engine.retrieve()`: `RAG_RERANK=1`이면 후보 15개 → 재정렬 → 상위 8개(서비스 기존 top_k). 꺼져 있으면 기존과 동일.
  - 재정렬 전용 LLM은 timeout 8초·재시도 0 → 느려도 30초 요청 한도 안에서 검색 순서로 대체.
  - 로그: `rerank candidates=15 kept=8 ms=…` (응답 시간 측정용)
- `infra/docker-compose.yml`: rag 서비스에 `RAG_RERANK: "1"` (끄려면 "0" 후 rag 재기동).
- 테스트: `tests/test_rerank.py` 6개 추가(순서 적용·누락/중복 번호·실패 시 원래 순서·Engine 켜기/끄기). 전체 46개 통과.
- 실험과 다른 점: 서비스는 원래 질문이 아니라 agent가 만든 검색어(용어 사전 덧붙임)로 검색·재정렬하고, 상위 5개가 아닌 8개를 LLM에 넘긴다.
  → 서비스 경로 효과는 `evaluate-answers`로 다시 측정해야 함(미측정).

## 5. 답변 실패 원인 분석·수정 1 — 청크 끝에 홀로 남은 제목 (2026-10-25)
- 증상: K5 "엔진 경고등" 질문이 "설명서에서 근거를 찾지 못했어요"로 끝남(API 직접 테스트 12건 중 4건 실패).
- 진단(`debug_engine_light.py`, 답변·검증 LLM 원본 출력): 답변 LLM은 정상 답변(missing_terms 없음)을 냈지만
  **검증 LLM이 "근거 없음"으로 탈락** → 재시도도 탈락 → not_found.
  - 처음 의심한 "주황색" 단어는 원인이 아님(같은 질문이 재시도에서 통과하기도 함 → LLM 판정이 흔들리는 문제).
- 원인: 1,000자 단위로 자르면서 "엔진 경고등" 제목이 앞 청크 마지막 줄에 남고 설명은 다음 청크("(계속)")로 넘어감.
  검증기는 "답변이 질문한 대상과 같은 항목의 근거에서 왔는가"를 보는데, 설명 앞에 경고등 이름이 없어 판단 불가 → 탈락.
  - 전체에서 같은 패턴 157개 청크(제목·"경고"·"주의" 라벨 등). 경고등만 해도 엔진·엔진오일 압력·EPB·전방 안전 등.
- 수정:
  - `core.chunk_manual_pages`: 자를 때 마지막 줄이 제목이면 다음 청크로 넘김(앞으로 다시 만드는 인덱스).
  - `core.carry_dangling_headings` + `scripts/carry_headings_index.py`: 기존 v13b를 고쳐 `v13c-headings` 생성.
    청크 ID 유지(평가셋 호환), 바뀐 157개만 재임베딩.
  - compose `RAG_INDEX` → `v13c-headings`.
  - 테스트 `tests/test_headings.py` 3개(제목 판별, 이동, 옮기면 안 되는 경우). 전체 49개 통과.
- 남은 문제: 브레이크 경고등은 제목·설명이 한 청크에 있는데도 검증 탈락 → 검증기 쪽 원인 별도 분석 필요.

## 6. 답변 실패 원인 분석·수정 2 — 검증 모델 (2026-10-25)
- v13c(제목 수정) 후에도 엔진·브레이크 경고등은 실패: 검색은 좋아졌지만(엔진 경고등 청크 1위) 검증 LLM이 계속 탈락시킴.
- 진단(`debug_verify.py`): 같은 답변을 검증 조건만 바꿔 3번씩 판정.

  | 질문 | V1 지금(gpt-4o-mini, 청크 8개) | V2 인용 청크만(mini) | V3 gpt-4o(청크 8개) |
  |---|---|---|---|
  | 엔진 경고등 | 0/3 | 0/3 | **3/3** |
  | 브레이크 경고등 | 0/3 | 0/3 | **3/3** |
  | 엔진오일 압력(앱에서는 성공) | 0/3 | 3/3 | **3/3** |

  - mini는 매번 같은 판정(0/3) → 우연이 아니라 모델 한계. 근거를 줄여도(V2) 엔진·브레이크는 해결 안 됨.
  - 엔진오일 압력도 이 답변으로는 mini가 탈락 → 앱에서 성공한 건 재시도 답변이 우연히 통과했기 때문(추론).
- 수정: 검증만 gpt-4o로 분리. `Engine(verify_model=…)`, 환경변수 `RAG_VERIFY_MODEL`(compose: gpt-4o). 분류·답변·재정렬은 gpt-4o-mini 유지.
  기본값은 기존과 같음(설정 없으면 llm_model). 테스트 1개 추가, 전체 50개 통과.
- 주의: server.py 기존 주석에 "더 강한 검증기가 맞는 답을 탈락시켰다"는 반대 기록이 있음 → gpt-4o가 지나치게 관대해지지 않았는지
  틀린 문장을 끼운 대조군으로 확인 필요(`debug_verify.py` 대조군 줄). 비용·지연 증가도 측정 필요.

| 원문 줄바꿈·띄어쓰기 | 규칙 추가·줄바꿈 정리·둘 다 3회씩 | 모두 0/3 → 원인 아님 |
- 남은 단서: 15:28 실행에서는 gpt-4o가 같은 엔진 답변을 3/3 통과. 차이는 함께 넘어간 나머지 청크 7개(재정렬 결과마다 바뀜,
  7,570자 vs 5,358자). 다른 경고등 설명이 섞인 근거 묶음이 판정에 영향을 주는지 미확인.
- 검증기가 밝힌 탈락 이유는 "'배기가스 제어 센서'가 근거에 명시되지 않음"처럼 원문과 거의 같은 표현을 거부하는 형태.

## 8. 남겨 둘 개선 과제 (우선순위 순)
1. **엔진 경고등 검증 탈락 원인 확정** — 다음 실험: 검증기에 엔진 청크만 단독으로 넘겨 통과하는지 → 통과하면 검증 근거를
   "인용한 청크 + 같은 경고등 항목"으로 좁히는 방향. (근거: §7 남은 단서)
2. **재시도 방식** — 검증 탈락 시 "그 문장을 빼라" 피드백 때문에 의미·위험 설명이 빠진 반쪽 답변이 통과하는 경우가 있음
   (A3 2차 답변: "지금 할 일"만 남음). 핵심 항목(무슨 뜻)이 빠지면 통과로 보지 않는 기준 필요.
3. **경고등 용어 매핑** — K5 설명서에는 "냉각수 경고등" 항목이 없고 "엔진 과열"·LCD 메시지로 설명됨. 사용자 표현 →
   설명서 항목 사전(warning_lights.json 별칭)에 추가하고, 이 경우 "설명서는 엔진 과열 항목으로 안내" 같은 연결 문장을 허용할지 결정.
4. **응답 시간** — 목표 3~5초 대비 성공 5~7초, 실패 11~16초.
   - `core.search`가 요청마다 인덱스 파일(~20MB)을 다시 읽고 sha256을 계산 → 서버 시작 시 1회 로드로 변경(효과 미측정).
   - 재시도 횟수·답변 최대 길이(500토큰) 조정, 단계별 소요 시간 로그 추가.
5. **경고등 청크 구조** — 1,000자 단위라 한 청크에 경고등 3~5개 설명이 섞임. 경고등 섹션은 경고등 1개 = 청크 1개로 자르면
   검색·검증 모두 대상이 분명해질 것(추론). 인덱스 재생성 필요(청크 ID 변경 → 평가셋 정답 ID 재확인).
6. **평가 체계** — 평가셋 44문항 검토(draft → reviewed), 경고등 질문을 rag 평가에 추가(현재 rag 대상 23문항 중 경고등 1개),
   서비스 경로 그대로 `evaluate-answers`로 답변 품질(정확성·근거성·환각) 측정, 반복 측정으로 LLM 변동 폭 기록.
7. **비용** — 검증을 gpt-4o로 바꿔 질문당 약 $0.01 추가(입력 4~6천 토큰 추정, 단가는 제3자 자료 기준·미확인). 실제 사용량 로그로 확인.
8. **재정렬 변동** — temperature 0이어도 순위가 문항 1~2개씩 바뀜(MRR 0.80/0.86). 서비스 반영 후 같은 질문의 결과 흔들림 모니터링.
